Make the evaluation policy configurable

Replace a hidden threshold with an explicit policy value, without teaching assembly or routing about scoring rules.

The problem

Lesson 19 added a rule: fewer than 10 passing attempts means a quarterback is not evaluable. The rule belongs in the evaluator. The number 10 does not. It is a policy choice that will change as you compare slates, seasons, or scoring approaches.

Design question:
Which component chooses the minimum attempt count? Which component applies it? They are not the same component.

One small policy shape

In src/evaluation.ts, define the configuration the evaluator needs:

export interface QuarterbackEvaluationPolicy {
  readonly minimumPassingAttempts: number;
}

An interface names the required shape. The evaluator will accept any object with that property. The readonly marker says evaluation may read the threshold but may not change it.

Red: prove the number is an input

Add this test to test/application.test.ts. A quarterback with 35 attempts scores under the normal policy. Under a policy requiring 40 attempts, the same quarterback is not evaluable.

test("The policy supplies the minimum attempts", () => {
  const recorder = dependencyRecorder();
  const strictPolicy = { minimumPassingAttempts: 40 };
  const dependencies: ApplicationDependencies = {
    ...recorder.dependencies,
    evaluate: (candidate) => evaluateQuarterback(candidate, strictPolicy),
  };

  const result = runQuarterbackEvaluation(baseInput, dependencies);

  assert.deepEqual(result, {
    kind: "evaluation-complete",
    evaluation: {
      kind: "not-evaluable",
      playerId: "player-1",
      displayName: "Example Quarterback",
      reason: "insufficient-attempts",
    },
  });
});

Run npm test. First, TypeScript should reject the extra policy argument because the evaluator's signature does not accept it yet. After you add the parameter in the next step, run the test again. It should then fail because the evaluator still compares against its hidden 10.

Green: pass the policy to the evaluator

Change the evaluator signature:

export function evaluateQuarterback(
  candidate: QuarterbackCandidate,
  policy: QuarterbackEvaluationPolicy,
): EvaluationResult

Then replace the hard-coded comparison with:

if (candidate.passingAttempts.value < policy.minimumPassingAttempts) {

Wire it once

In src/main.ts, choose the policy next to the program's other assembled dependencies:

const evaluationPolicy = { minimumPassingAttempts: 10 };

const result = runQuarterbackEvaluation(input, {
  evaluate: (candidate) => evaluateQuarterback(candidate, evaluationPolicy),
  // other dependencies
});

The arrow function is a wrapper. It gives the application the one-argument evaluate function it expects, while supplying the evaluator's policy from the composition root.

Check the boundary

Run:

npm run typecheck
npm test
git diff -- src/evaluation.ts src/main.ts test/application.test.ts

You should have six passing tests. Do not change src/domain.ts, src/application.ts, src/assembly.ts, or src/presentation.ts. The policy belongs to the evaluator. Application routing should not need to know its threshold.

Explain the result

  1. Why is minimumPassingAttempts a policy value rather than a hard-coded evaluator detail?
  2. Why does main.ts choose the policy while evaluation.ts applies it?
  3. Why is the wrapper function in main.ts useful?

Primary source

Read the official TypeScript Handbook section on function type expressions. Connect (candidate) => evaluateQuarterback(candidate, evaluationPolicy) to the evaluate function type in ApplicationDependencies.

Done when

Six tests pass, type checking passes, changing the policy from 10 to 40 changes the evaluation outcome, and you can explain why application routing did not change.
