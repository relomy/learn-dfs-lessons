Route assembly outcomes

Let the use case choose what happens next without taking over scoring or presentation.

The use case is the traffic controller

Candidate assembly now returns Ready, NeedsReview, or Rejected. The use case reads that result and calls the appropriate collaborator. It coordinates the work. It does not perform every part of the work itself.

Ready        → evaluator.evaluate(candidate)
NeedsReview  → reviewQueue.add(reason, evidence)
Rejected     → diagnostics.record(reason, source)
Coordination rule:
The use case chooses the next operation. The called component owns how that operation works.

Follow one Ready result

The use case receives Ready(candidate) and calls the evaluation policy. The policy may return a score or NotEvaluable. The use case then returns that application result to a presenter. The presenter decides whether the outside world sees a table row, JSON, or a CLI message.

Practice the boundary

Classify each proposed responsibility. Choose Route when the use case coordinates collaborators, Score when the evaluation policy owns the decision, and Shape when a presenter owns the external form. There are twelve cases before the set repeats.

Transfer check

The evaluator returns NotEvaluable because passing attempts are unknown. Describe what the use case should do next. Then name one thing it must leave to the presenter.

Primary source

Read Alistair Cockburn's original Hexagonal Architecture article. Focus on the claim that the application should run without intimate knowledge of its input and output technologies. Our use case can coordinate the same behavior whether the result eventually reaches a CLI, API, or test.

Done when

You can trace all three assembly outcomes, identify the next collaborator, and keep scoring rules and output formatting out of the use case.
