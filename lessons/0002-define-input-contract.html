Lesson 2 · DFS analytics architecture

Define the input contract

A file can be valid CSV and still be unusable for our domain.

The idea

An input contract records what a source gives us, what the values mean, and what quality the system expects. It is the agreement at the boundary between a source adapter and the rest of the system.

The DraftKings file has ten columns, but that does not mean all ten should become fields on every domain object. Some identify the source, some describe a slate entry, and some may be unnecessary for the first slice.

Our first-slice promise:
Given a DraftKings NFL main-slate salary file, produce a valid available QB pool sorted by salary. Do not produce a ranking yet.

Your exercise

Classify each field below as required, useful but not required, source metadata, derived, or not needed yet.

  • Position
  • Name + ID
  • Name
  • ID
  • Roster Position
  • Salary
  • Game Info
  • TeamAbbrev
  • AvgPointsPerGame
  • Status

Then answer:

  1. What should happen if a required field is missing?
  2. What should happen if one row has a malformed salary or game description?
  3. Which values should be copied into the domain model, and which should be translated first?

Primary source

Read RFC 4180 for the basic CSV conventions. The goal is not to memorize the specification. Notice the difference between the file format and the meaning our application assigns to each field.

Done when

You can justify every classification and describe the system’s response to invalid input.

Reply with your classifications and answers. Ask follow-up questions whenever a term or choice is unclear.
