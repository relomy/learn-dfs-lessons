Lesson 24 · DFS analytics architecture

Carry team identity through assembly

Give a quarterback candidate the team code it needs to receive team-level context later.

The missing join key

You can now turn an nflverse row into two TeamGameContext values. But a QuarterbackCandidate has no team, so there is no way to select the context that belongs to that quarterback.

Normalized QB input
team: "HOU"
→
Quarterback candidate
team: "HOU"
→
Later: match team context

Make team part of the domain contract

In src/domain.ts, add the same field to both interfaces:

export interface NormalizedQuarterbackInput {
  // existing fields
  readonly team: string;
}

export interface QuarterbackCandidate {
  // existing fields
  readonly team: string;
}

Use the existing three-letter code convention for this lesson. We can model a stronger team-code type only when the application needs validation or translation across providers.

Red: test direct assembly

Create test/assembly.test.ts. Start with a complete NormalizedQuarterbackInput using team: "HOU". Call assembleQuarterbackCandidate directly.

Assert the ready result includes the team:

assert.deepEqual(result, {
  kind: "ready",
  candidate: {
    playerId: "player-1",
    slateId: "nfl-week-1-main",
    displayName: "Example Quarterback",
    team: "HOU",
    salary: { cents: 740000 },
    passingYards: { kind: "known", value: 280 },
    passingAttempts: { kind: "known", value: 35 },
  },
});

Run npm test. The compiler will point out every existing normalized-input fixture that must now state a team. That is useful. The type made a new required domain fact visible everywhere it enters the application.

Green: preserve the value

In assembleQuarterbackCandidate, copy input.team onto the ready candidate. Then add team to the input fixture in src/main.ts and every test fixture that creates a complete NormalizedQuarterbackInput.

Keep this change small

Do not add a team to EvaluationResult, and do not change evaluateQuarterback. The evaluator does not use team identity yet. Carrying a fact through the candidate is enough to unlock the next join.

Explain the result

  1. Why is team identity needed on a quarterback candidate before we can use team game context?
  2. Why does TypeScript force updates to every complete input fixture after this field becomes required?
  3. Why should the evaluator remain unchanged in this lesson?

Primary source

Read TypeScript's object-types guide. Required object properties are the compiler's way of keeping every construction site honest.

Done when

A ready candidate carries team: "HOU", all fixtures compile with an explicit team, and the evaluator's API has not changed.

Ask if the compiler reports an object that looks unrelated. It is showing another place that constructs the domain contract.
