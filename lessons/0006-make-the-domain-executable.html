Make the domain executable

Turn the model’s rules into a small, testable first slice.

The idea

A model becomes useful when its rules can be exercised. Start with a narrow path through the system: one raw row becomes one Player and one SlatePlayer, or is rejected with a reason. Keep the path small enough that every transformation is visible.

Vertical slice:
One thin path through the boundary that proves the important pieces work together.

One possible flow

raw row
  → parse source fields
  → create Player
  → create SlatePlayer
  → accepted, or rejected with a reason

The adapter should be responsible for translation. The domain object should be responsible for protecting its invariants. A test can then prove both the happy path and a meaningful rejection without testing every possible CSV variation.

Your exercise

  1. Write pseudocode for creating one valid SlatePlayer from a raw row.
  2. Choose two malformed rows and state whether each is rejected by the adapter or refused by the domain model.
  3. Write three test names that would demonstrate the first slice works.
  4. Identify one piece of behavior that should not be included yet.

Keep sorting and quarterback selection outside this exercise. The goal is to prove the translation and domain rules before adding use-case behavior.

Primary source

Done when

You can trace one row from source input to a valid domain object, explain where invalid data is stopped, and name a test that would catch a broken invariant.
