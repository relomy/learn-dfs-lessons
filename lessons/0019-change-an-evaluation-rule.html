Change an evaluation rule

Use one failing test to add a minimum-attempts rule without changing assembly or routing.

The new rule

A quarterback with 1 through 9 known passing attempts has too little data for this evaluation policy. The candidate remains valid, but the policy returns not-evaluable with reason insufficient-attempts.

Prediction before code:
Which files should change? Write down your answer before reading the steps below.

Three pieces of TypeScript

You only need three pieces of syntax for this change.

A property type

const input: NormalizedQuarterbackInput = { ... };

The text after : tells TypeScript what shape input must have. This is close to a Python variable annotation such as input: NormalizedQuarterbackInput.

Object spread

const input = {
  ...baseInput,
  passingAttempts: { kind: "known", value: 7 },
};

...baseInput copies the existing properties. The later passingAttempts property replaces the copied one. The Python dictionary equivalent is {**base_input, "passingAttempts": ...}.

A union of exact strings

reason:
  | "missing-passing-data"
  | "no-passing-attempts"
  | "insufficient-attempts";

Each quoted value is both text and an allowed literal type. The | means "or." TypeScript will reject any other reason.

Red: add one failing example

Add this test to test/application.test.ts:

test("Too few attempts are not evaluable", () => {
  const recorder = dependencyRecorder();
  const input: NormalizedQuarterbackInput = {
    ...baseInput,
    passingAttempts: { kind: "known", value: 7 },
  };

  const result = runQuarterbackEvaluation(input, recorder.dependencies);

  assert.deepEqual(result, {
    kind: "evaluation-complete",
    evaluation: {
      kind: "not-evaluable",
      playerId: "player-1",
      displayName: "Example Quarterback",
      reason: "insufficient-attempts",
    },
  });
});

Run npm test. The failure should show that the policy returned scored. That failure is useful. It proves the test can detect the missing rule.

Green: teach the type, then the policy

First, open src/domain.ts. Add "insufficient-attempts" to the allowed reasons for the not-evaluable variant of EvaluationResult.

Next, open src/evaluation.ts. Keep the zero-attempt check as its own case. Immediately after it, add:

if (candidate.passingAttempts.value < 10) {
  return {
    kind: "not-evaluable",
    playerId: candidate.playerId,
    displayName: candidate.displayName,
    reason: "insufficient-attempts",
  };
}

Run:

npm run typecheck
npm test

You should now have five passing tests.

Check the boundary

Run:

git diff -- src/domain.ts src/evaluation.ts test/application.test.ts
git diff -- src/assembly.ts src/application.ts

The first command should show your type, policy, and test changes. The second should show nothing. Assembly still decides whether it can construct a candidate. The use case still routes the same outcomes. Only the evaluation contract and policy changed.

Explain the result

Answer these from memory:

  1. Why is a candidate with seven attempts valid but not evaluable?
  2. Why did domain.ts change along with evaluation.ts?
  3. What does the | mean in the reason type?

Five tests pass, type checking passes, assembly and application remain unchanged, and you can answer the three questions above without looking at the files.
