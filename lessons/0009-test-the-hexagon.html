Lesson 9 · DFS analytics architecture

Test the hexagon

Put each test at the boundary where its knowledge belongs.

The idea

Hexagonal architecture is valuable partly because the application can be tested without its external technologies. Each test should know only the boundary it is verifying.

Test boundary rule:
Test domain rules with domain values, adapters with representative source data, and use cases with substitute ports.

Three useful test perspectives

  • Domain test: proves rules such as non-negative salary or valid availability without reading a CSV.
  • Adapter test: proves a DraftKings row becomes the intended domain values and malformed source data is handled.
  • Use-case test: supplies a fake PlayerSource and proves application behavior without DraftKings or a file.

An integration test can connect the real pieces and catch wiring or format mismatches. It is useful, but it should not be the only way to discover a broken domain rule.

Boundary diagram

domain rule  ←  domain test
source row   ←  adapter test  →  PlayerSource
use case     ←  fake source
full wiring  ←  integration test
