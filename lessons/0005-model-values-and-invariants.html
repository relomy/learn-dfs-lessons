Model values and invariants

Make invalid domain states harder to create.

The idea

A domain model is more than a bag of strings and numbers. Some values have meaning and rules: a salary is money, a position comes from a known vocabulary, and a matchup has two teams and a kickoff. Modeling those rules explicitly gives the rest of the system safer building blocks.

Invariant:
A rule that must be true whenever a domain object exists.

Possible first-slice values

  • Salary: non-negative currency amount.
  • Position: one of the positions supported by the domain.
  • Availability: a domain value such as available, questionable, or unavailable.
  • Matchup: away team, home team, and scheduled kickoff.

These could begin as ordinary fields with validation in constructors. A dedicated value object is justified when it makes a rule, operation, or boundary clearer—not merely because a noun exists.

Your exercise

  1. Sketch a SlatePlayer with Player, position, salary, matchup, team, and availability.
  2. Write three invariants that must hold for every valid SlatePlayer.
  3. Choose one field that deserves a value object now, and one that should remain simple for now.
  4. For each choice, explain what rule or behavior justifies it.

Do not design a complete hierarchy. Keep the first QB slice small and make the rules visible.

Primary source

Read Martin Fowler’s explanation of Value Objects. Focus on the difference between a value’s identity and the meaning carried by its attributes.

Done when

You can state the rules that make a SlatePlayer valid and explain why one value deserves explicit modeling without prematurely abstracting everything.

Reply with your sketch, invariants, and modeling choices. Ask follow-up questions whenever a term or choice is unclear.
