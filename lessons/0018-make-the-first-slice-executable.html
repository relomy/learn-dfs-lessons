The language decision

We are using TypeScript. It is new enough to make the implementation educational, but its discriminated unions fit the Ready, NeedsReview, and Rejected model you already designed. The compiler can narrow each branch by its kind field.

The language is not a second curriculum. For this slice, you need only object types, unions, functions, imports, and switch.

Implementation rule:
Keep the first slice small enough that every file has one reason to change.

Run it before reading it

From the repository root, run:

npm test
npm start

Example Quarterback: 8.00 passing yards per attempt

Trace the running path

  1. main.ts supplies one in-memory normalized input.
  2. application.ts asks assembly for an outcome and routes it.
  3. assembly.ts returns Ready, NeedsReview, or Rejected.
  4. evaluation.ts owns the yards-per-attempt policy and NotEvaluable decision.
  5. presentation.ts turns the application result into console text.

See the type doing architectural work

Open domain.ts and find AssemblyResult. Each variant carries different data. The candidate also stores salary as integer cents, preserving the money decision from Lesson 5. In application.ts, the switch checks assembly.kind. Inside each branch, TypeScript exposes only the fields valid for that outcome. This is the code version of Lessons 15 through 17.

Your experiment

Before editing, predict what should happen if passing attempts become unknown. Then change this line in main.ts:

passingAttempts: { kind: "known", value: 35 },

to:

passingAttempts: { kind: "unknown" },

Run npm start again. Assembly should still return Ready because the candidate is valid. Evaluation should return NotEvaluable because this policy needs passing attempts. The presenter should print that result. Restore the original line when you finish.

The automated feedback

application.test.ts exercises all three assembly paths. A fourth test proves that Ready may still become NotEvaluable inside the policy. Run npm test after every experiment.
