Lesson 4 · DFS analytics architecture

Separate player from slate data

Give each concept the facts that remain true when the slate changes.

The idea

A Player identifies a person in the domain. A slate-specific record describes that player’s participation in one contest context. Keeping those apart prevents facts that change per slate from being mistaken for permanent player attributes.

Modeling test:
If the same player appears on tomorrow’s slate, which values can change without the person changing?

Start with facts

  • Player: name and stable identity.
  • Slate-specific concept: salary, matchup, availability, team, and eligible position.

The second concept might be called SlatePlayer, PlayerPoolEntry, or something else. The name is not the decision yet. It should make the application’s language clearer to the people using and maintaining it.

Your exercise

  1. Choose two candidate names for the slate-specific concept.
  2. For each name, write one sentence describing what an instance represents.
  3. Decide where salary, matchup, and availability belong, and explain why.
  4. Describe one future requirement that would make your chosen name feel wrong.

You do not need to write code. Make the model precise enough that the adapter could create it from a raw row.

Primary source

Read Martin Fowler’s overview of Domain-Driven Design with one question in mind: which names would make the DFS problem easier to discuss?

Done when

You can explain why a player and a player’s slate participation are different concepts, and defend a name for the slate-specific concept using the first-slice use cases.
