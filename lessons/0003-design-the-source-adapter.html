Lesson 3 · DFS analytics architecture

Design the source adapter

Give the rest of the system a clean boundary, even when the source is messy.

The idea

An adapter is a translator at the edge of the system. It knows DraftKings column names, string formats, and status codes. The domain should know players, slate entries, matchups, salaries, and availability—not the quirks of a CSV provider.

Boundary rule:
Parse and validate once at the edge. Pass meaningful domain values inward.

What belongs where?

  • Source adapter: open CSV, check headers, parse salary, parse game information, and translate status.
  • Domain: represent `Player`, `Matchup`, and `SlateEntry`; enforce invariants such as a non-negative salary.
  • Use case: select quarterbacks who are available and sort them by salary.

A useful test is this: if DraftKings renamed Game Info to Matchup, how many layers should change? Ideally, one adapter and its tests.

Your exercise

Sketch the adapter’s public boundary in plain language or pseudocode. Include:

  1. what it accepts;
  2. what it returns for valid rows;
  3. how it reports rejected rows; and
  4. which DraftKings details must not leak beyond the boundary.

Then inspect the existing prototype and identify one detail that currently leaks source concerns into the domain model.

Primary source

Read the Python CSV module documentation just far enough to notice that reading rows is separate from deciding what those rows mean. That separation is the architectural seam.

Done when

You can describe the adapter without mentioning sorting or QB selection, and you can explain why a rejected row is different from a failed import.

Reply with your boundary sketch and the leaking detail. Ask follow-up questions whenever a term or choice is unclear.
