Test the policy boundary

Prove that the evaluator excludes values below the minimum and includes the minimum itself.

The boundary is the rule

The policy says a quarterback needs at least 10 passing attempts. That sentence has two important examples:

9 attempts  → not-evaluable
10 attempts → scored

Testing only 7 attempts proves that some low values are excluded. It does not prove whether 10 is included. The pair above does.

Prediction before code:
If the comparison accidentally becomes <=, which test fails? Explain why before you run it.

Test the evaluator directly

Create test/evaluation.test.ts. This test does not need assembly, routing, or a dependency recorder. It asks the evaluator one focused question.

import assert from "node:assert/strict";
import test from "node:test";

import type { QuarterbackCandidate } from "../src/domain.js";
import { evaluateQuarterback } from "../src/evaluation.js";

const policy = { minimumPassingAttempts: 10 };
const baseCandidate: QuarterbackCandidate = {
  playerId: "player-1",
  slateId: "nfl-week-1-main",
  displayName: "Example Quarterback",
  salary: { cents: 740000 },
  passingYards: { kind: "known", value: 280 },
  passingAttempts: { kind: "known", value: 10 },
};

Add the two examples

test("Attempts below the minimum are not evaluable", () => {
  const candidate: QuarterbackCandidate = {
    ...baseCandidate,
    passingAttempts: { kind: "known", value: 9 },
  };

  assert.deepEqual(evaluateQuarterback(candidate, policy), {
    kind: "not-evaluable",
    playerId: "player-1",
    displayName: "Example Quarterback",
    reason: "insufficient-attempts",
  });
});

test("The minimum number of attempts is evaluable", () => {
  assert.deepEqual(evaluateQuarterback(baseCandidate, policy), {
    kind: "scored",
    playerId: "player-1",
    displayName: "Example Quarterback",
    yardsPerAttempt: 28,
  });
});

Use the feedback loop

Run npm test. Both tests should pass. Then, only as an experiment, change this line in src/evaluation.ts:

candidate.passingAttempts.value < policy.minimumPassingAttempts

to:

candidate.passingAttempts.value <= policy.minimumPassingAttempts

Run npm test again. The 10-attempt test should fail. Restore < when you finish.

Why this test belongs here

The application test from Lesson 20 proves that application wiring supplies a chosen policy. This new test proves the evaluator's own behavior. Both test different things. A direct test makes the policy rule easier to read and faster to diagnose.

Explain the result

  1. Why do you need both the 9-attempt and 10-attempt examples?
  2. Why does changing < to <= break only one of those tests?
  3. Why does this test call evaluateQuarterback directly instead of runQuarterbackEvaluation?
